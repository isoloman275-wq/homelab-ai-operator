# AMD Radeon on Ollama — RX 580 fit session (2026-09-03, lab-specific worked example)

AUX-NODE's GTX 960 died in an upgrade; RX 580 4GB went in. Session = wiring AMD GPU inference + 2-4B model bake-off under a hard 64K-context floor (Hermes agent minimum).

## Root cause chain (why the GPU "wasn't there")
1. `/api/ps` showed `size_vram: 0` → CPU-only inference (11.7 tok/s).
2. The AUX-NODE Ollama install was a **stripped manual copy** from the old 960 fix — only `ggml-cpu-*` DLLs, NO rocm/vulkan dirs. Lesson: a manually-copied Ollama install silently loses all GPU backends.
3. Fix = install the full official `OllamaSetup.exe` (silent flags: `/VERYSILENT /NORESTART /SUPPRESSMSGBOXES`). Gotchas hit: (a) Start-Process over SSH had quoting hell + zone-identifier blocking — the reliable path was **write a .ps1 locally, push it via `$input | Set-Content` over ssh, run with `-ExecutionPolicy Bypass -File`**; (b) the installer removes the old lib dir first — models in `~\.ollama\models` survive, but verify `ollama list` after; (c) full install = 2.8GB with `rocm_v7_1/`, `vulkan/`, `cuda_v12/13/` dirs — that's how you know it's complete.
4. The OllamaServe scheduled-task watchdog survived the reinstall (service re-registered under `ollama app`).

## RX 580 (gfx803/Polaris) fit reality — measured
- **2B Q4 fits 100% VRAM @ 64K ctx**: qwen3.5:2b-aux = 2.39/2.39GB, 28.4 tok/s (vs 11.7 CPU-only).
- **3B Q4 does NOT fully fit**: granite4.1:3b-q4_K_S = 2.36GB weights in VRAM but total footprint w/ 64K KV = 7.5GB → hybrid, 19.5 tok/s (still very usable).
- **4B Q4 = fail**: qwen3.5:4b only 2.0/3.7GB offloaded → 7 tok/s. gfx803's ROCm caps usable offload at ~2GB; Vulkan dir exists but Ollama didn't auto-improve beyond that.
- **Rule of thumb: RX 580 4GB ceiling = 2B-class at 64K ctx, or 3B-class hybrid at degraded speed.** Verify with `/api/ps` `size_vram` vs `size` — the ratio IS the GPU-offload fraction.
- `ollama.com` default tags can be FP16 (granite4.1:3b was 7.6GB!) — check `ollama list` disk size and prefer explicit `-q4_K_S` style tags.

## 2-4B tool-calling bake-off (no-reasoning requirement, BFCL-informed)
| Model | VRAM fit | tok/s | Tool calls | Verdict |
|---|---|---|---|---|
| granite4.1:3b-q4_K_S | partial (2.36GB) | 19.5 | **Best** — smart enum inference (added `unit:celsius` unprompted); BFCL-v3 60-74 published | KEPT — quality lane |
| qwen3.5:2b-aux | 100% | 28.4 | Clean native calls | KEPT — speed lane |
| qwen3.5:4b | ~54% | 7.1 | Clean native calls | DELETED — too slow |
| llama3.2-3b / Ministral-3-3b | not tested | — | — | Granite beat them on paper (BFCL) |
- Tool-call test pattern: simple weather tool (happy path), then an **irrelevant-tool probe** ("capital of France, use the get_weather tool") — Granite followed the explicit instruction (called it anyway); that's instruction-following, not tool-judgment failure. Keep the distinction when evaluating.
- No-reasoning verification: response `content` must be the answer with zero `<think>` spillover; both Qwen3.5 and Granite pass via Ollama native tool calling.

## Session gotchas
- `/api/ps` `expires_at` showing year 2318 = keep_alive effectively infinite (fine).
- Ollama server logs on Windows: `%LOCALAPPDATA%\Ollama\server*.log`, rotated server-2..5.log — binding-error spam in old ones is historical noise. Push a tiny .ps1 reader over SSH instead of fighting inline quoting.
- Hermes 64K context floor means AUX-NODE can only run swarm workers on ≤3B-class on this card. Quality-critical tool work at 64K on 4GB VRAM is a contradiction — pick two of {model size, context, full-VRAM}.

## Real-task validation (end of session)
Granite's bake-off win was confirmed with production work, not just toy tool probes: fed the actual backup inventory + Desktop listing from a client PC-repair job, it produced a technician-grade restore plan (restore-first / on-request / do-not-restore / extract-before-delete sections — the do-not-restore section correctly excluded AppData/NTUSER.DAT) plus a game-shortcut re-create list from a 14-line listing, in ~43s. Pattern: feed real inventory data + a structured-output prompt with named sections; verify section 3 (exclusions) is correct — that's where a bad model poisons a reinstall. This is AUX-NODE's ongoing role: LAN extraction/classification worker for jobs that don't need the 27B and must not touch GPU-NODE.
